# Alembic migration workflow

1. State the data-model change, reason, affected readers/writers, and rollback expectations.
2. Inspect the current SQLAlchemy model, latest migration heads, naming conventions, and tests.
3. Separate schema migration from data backfill when size, locking, or rollback risk justifies it.
4. Preserve compatibility during rolling or staged deployment when old and new code may overlap.
5. Write explicit upgrade and downgrade operations; do not trust autogenerated output without review.
6. For non-null columns, define a safe sequence: nullable/add default -> backfill -> constraint, as appropriate.
7. Consider indexes, uniqueness, foreign-key behavior, cascades, and PostgreSQL-specific types/extensions.
8. Never place credentials or real customer data in migrations or fixtures.
9. Verify migration from a clean database and, when relevant, from a representative previous revision.
10. Run focused persistence tests and the full suite for shared schema changes.

## Required report

- revision and parent revision;
- forward compatibility and downgrade behavior;
- lock/data-loss risk;
- commands actually run;
- any manual operational step required before deployment.
