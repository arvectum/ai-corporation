# Ручная экспертная эскалация в пилоте

## 1. Назначение

Экспертная эскалация — это управляемая ручная проверка сложного кейса специалистом Arvectum. Она не является автоматическим решением, юридическим заключением или гарантией допуска/победы.

В ARV-042 зафиксирован операционный порядок эскалации. Продуктовый workflow, роли экспертов, SLA, коммерческий контроль и immutable audit trail реализованы в ARV-052 и описаны в [Expert_Review_Workflow.md](../product/Expert_Review_Workflow.md).

## 2. Когда требуется эскалация

Оператор обязан инициировать эскалацию, если присутствует хотя бы один из признаков:

- отсутствует существенная часть документации;
- скан или таблица нечитаемы, а вывод зависит от спорного фрагмента;
- разные документы содержат противоречащие друг другу требования;
- источник вывода не удаётся однозначно связать с документом;
- обнаружено условие, способное изменить решение об участии;
- штрафы, обеспечения, гарантии, отсрочка или порядок оплаты выходят за профиль риска;
- требуется лицензия, СРО, сертификат, реестровая запись или иной обязательный допуск;
- расчёт экономики зависит от неподтверждённой цены, объёма, логистики или налога;
- модель или правило сформировали критический вывод с низкой уверенностью;
- оператор и система пришли к противоположным решениям;
- обнаружен возможный межклиентский доступ, неверная привязка run/артефакта или иной safety-инцидент.

## 3. Уровни

| Уровень | Описание | Действие | Целевой срок начала проверки |
|---|---|---|---|
| Sev-1 | Возможна ошибочная подача/отказ, существенный финансовый или договорный ущерб, утечка данных, неподтверждённый критический вывод | Немедленно блокировать `client_ready` и доставку | до 4 рабочих часов |
| Sev-2 | Существенная неточность или неоднозначность, требующая исправления/предупреждения | Оставить кейс в `operator_review` либо отправить на новый run | до следующего рабочего дня |
| Sev-3 | Некритичное улучшение качества, формулировки или удобства | Зафиксировать в backlog/weekly review; доставка возможна с явной пометкой | в рамках еженедельного разбора |

Сроки являются целевыми сервисными ориентирами пилота, а не публичным SLA продукта.

## 4. Карточка эскалации

Для каждой эскалации фиксируются:

| Поле | Содержание |
|---|---|
| Escalation ID | уникальный идентификатор |
| Customer / Project / Case / Run | точная область данных |
| Severity | Sev-1 / Sev-2 / Sev-3 |
| Инициатор | оператор Arvectum / оператор заказчика / автоматическая проверка целостности |
| Триггер | причина эскалации |
| Спорный вывод | что именно нельзя принять без проверки |
| Источники | документ, страница/раздел, файл, evidence ID |
| Потенциальное последствие | почему это важно |
| Требуемое решение | подтвердить / отклонить / уточнить / запросить данные / пересчитать |
| Эксперт | назначенный проверяющий |
| Дата открытия | |
| Целевой срок | |
| Решение | |
| Нужен новый run | да / нет |
| Клиентская пометка | что можно сообщить заказчику |
| Дата закрытия | |

В карточку не копируются секреты, токены и избыточные персональные данные.

## 5. Процесс

### Шаг 1. Блокировка или маркировка

- Sev-1: кейс не переводится в `client_ready`; доставка запрещена.
- Sev-2: кейс остаётся в `operator_review` либо возвращается в анализ.
- Sev-3: замечание фиксируется; оператор решает, влияет ли оно на текущую доставку.

### Шаг 2. Сбор доказательств

Оператор прикладывает только необходимые источники и указывает точное место в документе. Формулировка «модель считает» не является доказательством.

### Шаг 3. Ручная проверка

Эксперт:

1. проверяет исходный документ и контекст;
2. разделяет подтверждённые факты, интерпретации и неизвестные данные;
3. оценивает влияние на решение;
4. выбирает одно из решений:
   - `CONFIRMED`;
   - `REJECTED`;
   - `NEEDS_CUSTOMER_INPUT`;
   - `NEEDS_NEW_RUN`;
   - `BLOCK_CASE`.

### Шаг 4. Исправление

Утверждённый канонический результат и PDF не редактируются задним числом. Если решение меняет отчёт:

- создаётся новый AnalysisRun;
- формируется новый канонический результат;
- публикуется новый immutable PDF;
- проводится новая операторская проверка;
- предыдущий артефакт сохраняется в аудируемой истории.

### Шаг 5. Закрытие

Эскалация считается закрытой, когда:

- решение и доказательство зафиксированы;
- при необходимости завершён новый run;
- клиентская версия комментария подготовлена;
- feedback внесён в соответствующую категорию;
- Sev-1 больше не блокирует передачу либо кейс остановлен.

## 6. Лимит пилота

В стандартный пилот включено до 3 ручных экспертных проверок. Лимит считается по закрытым или принятым в работу карточкам Sev-1/Sev-2, а не по числу сообщений в обсуждении.

Дополнительная проверка оформляется по [pilot_commercial_terms.md](pilot_commercial_terms.md). Safety-инцидент, вызванный Arvectum, не списывается из коммерческого лимита заказчика.

## 7. Запрещённые практики

- выдавать предположение эксперта за юридическое заключение;
- исправлять утверждённый PDF без нового run;
- закрывать Sev-1 только текстовым комментарием без проверки источника;
- переносить данные одного заказчика в кейс другого;
- использовать эскалацию для обхода отсутствующих документов;
- обещать победу, допуск или конкретную экономию;
- передавать отчёт до завершения обязательной операторской проверки.

## 8. Еженедельный контроль

В KPI scorecard включаются:

- число эскалаций по severity;
- среднее и максимальное время до начала проверки;
- доля решений `CONFIRMED / REJECTED / NEEDS_NEW_RUN`;
- повторяющиеся причины;
- число Sev-1, открытых на конец недели;
- изменения профиля/правил, подтверждённые по результатам проверки.
